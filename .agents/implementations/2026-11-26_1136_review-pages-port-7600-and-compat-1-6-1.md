# 2026-11-26T11:36+08:00 — Review pages move to the 7600–7699 pool; compat matrix green on 1.3.0–1.6.1

Two things in this round: the port pool move (operator decision) and closing the compatibility gate that the previous round left unrun.

**Port pool 7600–7699.** `src/lib/web-review.ts` default `portStart` is 7600 and `portWalk()` still refuses to leave the hundred block, so the pool is 7600–7699 (100 ports) shared by `/ask-spec`, `/ask-uat` and `/ask-talk`. Talk's own `PORT_START` and `startTalkServer`'s fallback moved to 7600 too. Rationale recorded in the code and AGENTS.md: 34xx is routinely claimed by WSL / Windows port forwarders, and a review page that silently loses its port looks exactly like one that never started. Exhaustion still throws (`cannot bind a review server on ports 7600–7699`).

**Compatibility gate.** `pnpm check:compat` first surfaced two problems:
- pi **1.6.1** is published, so the window is now 1.3.0 / 1.4.0 / 1.5.0 / 1.5.1 / 1.5.2 / 1.6.0 / 1.6.1. Dist diff against 1.6.0: `compaction.js`, `compaction/utils.js`, `usage-totals.js`, `keybindings.js`, `model-selector.js`, pi-tui `select-list.js` / `settings-list.js` all byte-identical; `agent-session.js` only gains `fullOutputError` on the bash result; `types.d.ts` adds `blockedKind` on `ui.confirm/select/input` plus a comment rewrite; pi-tui `tui-alt-screen.js` adds right-click paste suppression for vscode/tabby — the search-key branch is still above `shouldDeferViewportInput()` (line 548 vs 570), so `ctrl+f` stays a dead key for the selector.
- Two window versions failed with `socket hang up` / `ECONNRESET` in HTTP tests. Cause: the matrix runs four sandboxes at once, and the tests were reusing ports (narrow random ranges collided inside a file) while the clients keep connections alive — a pooled socket outlives the server that opened it, so the next request dies. Fix: each test file now takes ports from a counter (`takePort()`, +3 per server) instead of a random offset, and the `node:http` helpers pass `agent: false` (fresh socket per call). `accepts only the first decision` also had a 50 ms window for its second request; it now uses 1000 ms and a 5 s `waitFor`, because `onDecision` is delivered on the close timer.
