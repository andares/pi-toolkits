# 2026-11-04T14:21:34+08:00 — 补建 0.1.0 的 tag 与 GitHub Release（历史缺口收口）

## 起因

发布 0.11.3 后按纪律跑 `pnpm release:github --audit`，退出码 1：19 个版本里只有 0.1.0
三列全红（npm 有、GitHub Release 无、远端 tag 无）。这是 0.1.0 时期 tag 还不在发布流程里
造成的历史缺口，AGENTS.md 的 Release 段一直以「历史缺口」登记；本次崔总决定补建。

## 先确认「该给哪个提交打 tag」

0.1.0 是老版本，凭印象打 tag 会把 Release 指到错误内容上。做法：把 npm 上的
`@andares/pi-toolkits@0.1.0` tarball 解包，逐文件与 git 历史候选提交做 sha256 比对。

- 候选来自 `git log -S'"version": "0.1.0"' -- package.json`：`8c3e7f5`（写入 0.1.0）、
  `dc716ab`（v0.2.0 发布时改成 0.2.0），中间若干提交都还是 0.1.0。
- 结果：tarball 的 9 个文件（`src/index.ts`、`src/features/ask/*`（5 个）、
  `src/lib/tools.ts`、`LICENSE`、`README.md`）与 **`8a0e2fb`** 的树哈希**全部一致**；
  `package.json` 只差 pnpm publish 改写后的键顺序（内容相同）。
- `8c3e7f5` 当时的 `src/` 还是空的，不可能是它；`0ba02e8` / `5298a60` 的文件哈希不同
  （那时 bash-sandbox 等还没经过后续格式化提交）。

## 执行

```text
git tag v0.1.0 8a0e2fbde0bbc54aa06c3a6ceba74192a50f78d9   # 轻量 tag，与 tag-current.mjs 同风格
git push origin refs/tags/v0.1.0                          # 远端校验：8a0e2fb…（一致）
POST /repos/andares/pi-toolkits/releases
     { tag_name: v0.1.0, name: v0.1.0,
       generate_release_notes: true,
       make_latest: "false",
       created_at: "2026-08-07T12:39:38+08:00" }
```

**为什么不是直接 `pnpm release:github v0.1.0`**：脚本建 Release 只发
`{tag_name, name, generate_release_notes}`，这样今天补出来的 0.1.0 会成为「最新的发布」——
既会把仓库的 Latest 徽标从 0.11.3 挪到 0.1.0，也会让下一次 `generate_release_notes`
以 0.1.0 为基线，把 2026-08 以来的全部提交灌进下一个 patch 版本的说明里。
崔总对本轮的要求是「不要对实际拉取最新版本的操作产生任何影响」，因此改用
`make_latest: false` + `created_at` 回填（GitHub 的 Create release 接口接受这两个字段，实测 201）。
tag 部分仍沿用脚本同样的两步（本地打 tag → 推送 → 远端哈希校验）。

Release 正文由 GitHub 生成（`**Full Changelog**` 指向 v0.1.0 的提交区），非草稿、非预发布。

## 残余风险

GitHub 的 «上一个发布» 判定没有公开契约；本次用 `created_at` 回填 + `make_latest:false`
把 0.1.0 排在 0.11.3 之后，但**下次发版时要看一眼 Release notes 的对比基线**——
如果发现 notes 把 8 月以来的提交全算进来，说明该判定走的是另一套顺序，届时改用
`generate-notes` 接口显式传 `previous_tag_name`（脚本目前不传）。
