## The failure it took to get there

Every attempt before that died at the OIDC exchange:

```text
POST /-/npm/v1/oidc/token/exchange/package/@andares%2fpi-toolkits  → 404
{"message":"OIDC token exchange error - package not found"}
```

with the same claims on every attempt (decoded from the id token of a read-only probe):

```text
aud = npm:registry.npmjs.org      repository = andares/pi-toolkits
sub = repo:andares@7556505/pi-toolkits@1326160051:environment:npm
job_workflow_ref = andares/pi-toolkits/.github/workflows/publish.yml@refs/heads/master
environment = npm
```

## Two wrong hypotheses, each killed by one experiment

| Hypothesis | Why it looked right | What falsified it |
| --- | --- | --- |
| npm registry cannot match GitHub's **immutable `sub`** claims ([npm/cli#9969](https://github.com/npm/cli/issues/9969)), and this repo (created 2026-08-07) is past the 2026-07-15 cutoff | the `sub` really does carry numeric IDs, and the upstream issue reports the identical message and pnpm error | `aliciai-dev/paintress` is **also** `use_immutable_subject: true` and publishes fine |
| **pnpm 12**'s own exchange implementation is broken, npm CLI would work | pnpm's warning + anonymous fallback is exactly the documented pnpm bug family | `npm publish --dry-run --loglevel verbose` in the same job got the **same** 404 |

Conclusion kept from the probes: the client is not the variable; the registry rejects the
exchange. `404 package not found` is npm's **masked** answer — a missing trusted publisher,
a mismatched workflow filename, or a mismatched environment all produce it, so the message
must be read as "check the registry-side record", never as "the package does not exist".

The operator re-created the trusted publisher entry for `@andares/pi-toolkits`; the next
dispatch published immediately. The entry had been created on the first pass but its fields
did not match what the workflow presents.

## Probe method worth keeping

Because `workflow_dispatch` runs the workflow file from the dispatched branch but checks out
`ref: inputs.tag`, a probe can be run without touching the tag:

- keep the file at `.github/workflows/publish.yml` — `job_workflow_ref` is part of what the
  registry matches, so a differently named probe file can only ever fail;
- `npm publish --provenance --dry-run --loglevel verbose` performs the full exchange and
  never publishes;
- `core.getIDToken` claims are visible by base64url-decoding the middle segment of the token.
